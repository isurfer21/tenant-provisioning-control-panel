# Language Recommendation: Go vs Python vs JavaScript

## Verdict: **Go (Recommended)**

| Criterion                                   | Go                                                                                                                      | Python                                                                                                                     | JavaScript / TypeScript                                                                                                                      |
|:--------------------------------------------|:------------------------------------------------------------------------------------------------------------------------|:---------------------------------------------------------------------------------------------------------------------------|:---------------------------------------------------------------------------------------------------------------------------------------------|
| Concurrency correctness                     | Built-in goroutines + channels — idiomatic, no shared-state pitfalls. Atomic operations for version checks are trivial. | GIL limits true parallelism; must use `asyncio` + processes or threads; harder to reason about race conditions under load. | Single-threaded event loop; concurrency via async/await patterns. No native threading — race conditions manifest differently and are subtle. |
| State machine accuracy                      | Enums + exhaustive switch (compiler-enforced) = no unhandled states.                                                    | `Enum` class + manual guards = runtime surprises.                                                                          | Enum types exist but fallibility is higher with unions + discriminants.                                                                      |
| Optimistic locking                          | `sqlc` or raw SQL → simple `UPDATE ... WHERE version = $1`.                                                             | SQLAlchemy / Prisma — ORM can obscure the row-lock semantics unless you're careful.                                        | TypeORM/Prisma — similar ORM concerns; driver-level lock handling is inconsistent.                                                           |
| Message broker support                      | NATS natively in Go (NATS.io); RabbitMQ go-amqp library is production-grade minimal.                                    | NATS has an excellent client; but async consumer model requires extra wiring.                                              | Consumer clients exist (nats.js, amqplib) but error-handling for at-least-once delivery and poison messages is more boilerplate-prone.       |
| Idempotent consumption                      | Simple map-sync + atomic DB checks — one goroutine per task id, or a bounded worker pool.                               | Must use asyncio primitives; harder to write correct without bugs.                                                         | Event loop coordination is tricky; requires external lock managers.                                                                          |
| Startup time / memory                       | Sub-second startup, ~10-20 MB heap. Ideal for containers and rapid dev cycles.                                          | 3-8 second cold start, 80-200 MB baseline. Noticeable Docker layer impact.                                                 | Moderate startup (~2s) depending on bundler/runtime used.                                                                                    |
| Static analysis                             | `gofmt` + `staticcheck` — zero-config, extremely fast, catches type errors pre-runtime.                                 | `flake8`/`ruff` + `mypy` — two tools, partial coverage (mypy is optional).                                                 | `prettier` + `eslint` — good but doesn't catch logic/state-machine bugs at lint time.                                                        |
| Zero secrets in repo                        | Single static binary — trivial `.dockerignore` and no dependency tree to audit.                                         | Virtualenv/pip — must audit `requirements.txt`; env files leak risk slightly higher.                                       | `node_modules` bloat; lockfile + package.json adds noise for a security scan.                                                                |
| Fits "boring, correct, well-tested" mandate | Yes — Go forces explicit error handling (`if err != nil`). No try/catch surprises.                                      | Decorators and exception chains hide control flow.                                                                         | Callbacks/promises make linear reading harder.                                                                                               |

## Conclusion

**Go is the unequivocal choice.** The assignment's core challenges — concurrency with optimistic locking, idempotent message consumption, deterministic state transitions, and correctness over cleverness — map directly to Go's design philosophy. Python would work but introduces unnecessary runtime uncertainty on all three critical paths. JavaScript is not a viable candidate for this type of infrastructure service.

> **Recommendation: Go** using `net/http` (standard library) or `gin` framework, SQLite (file-based, zero-config persistence), and NATS JetStream as the message broker. Docker Compose for local bootstrapping with one command.
